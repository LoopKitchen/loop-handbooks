loop · system handbook · 2026-09-08

The Import Engine

How Loop ingests customer CSVs: 15 typed templates declared in the repo, one three-tier validator, five server-side appliers, and one shared dialog mounted 21 times across three apps. This replaces all 20 CSVBox sheets that were in use. Every table row on these pages is a real row from dev loop_core (test chain 1199 · acme_14) or reproduced by running the shipped code; every rule is explained by the bug it prevents. Backend: cloud_endpoints/import_engine/ (worktree wt-import-engine, PR backend#20638). Frontend: packages/shared/src/ImportEngine/ (worktree wt-import-engine-fe, PR frontend#3937).

The system

Mental model

In plain terms. A template is a form definition, like a Google Form: the form itself (TEMPLATE), its fields (COLUMNs), some extra checks, and, for five templates, the code that saves (the applier). The three tiers are three levels of checking: cell = one cell alone ("is this an email?" — instant, in the browser), row = one row's cells together ("exactly one subtotal filled"), entity = the row against your real data ("is this location actually yours?" — server only). An option source is a named list of your things ("your locations") fetched live; the word "dropdown" in the code is a leftover from when these same lists filled CSVBox's pick-menus — today you type freely and the list checks what you typed. The idempotency claim is the double-click guard: a fingerprint of your rows is parked in Redis for 15 minutes and the identical submission is refused while it sits there; change any cell and it is a new fingerprint, accepted immediately. applyOverride is the escape hatch for templates with no applier: the dialog validates, then hands the clean rows to the page's own original save code.

A customer pastes or drops a CSV into a dialog. The dialog fetches the template for that import from the server (never cached, so the browser always renders the schema the server will validate against), checks what it can locally for instant feedback, then asks the server to validate all three tiers. Errors land on cells while the customer is still looking at the grid. Only when the report is clean (or the customer explicitly opts into a partial import) does apply run, and apply never invents a write path: it delegates each row to the endpoint that already owns the destination table.

The system

Templates & data model

In plain terms. The picture below is an entity-relationship diagram: boxes with fields, and lines meaning "one of these has many of those". Normally you would draw database tables this way; here the boxes are Python classes, because a template is code, not a table. Read TEMPLATE like the settings of a form: key = its unique name (a page mounts the dialog with templateKey="digital_stores" and that is the whole lookup); destination = where the data goes when you import, not which page opens it; upsert_key = the columns that identify a ROW — a matching row exists, it updates; otherwise it inserts; and two file rows with the same combo are duplicates; scope = whose data validation checks against (your chain's lists, your org's users, or one global list). A COLUMN is simply one column of the CSV.

There are no new database tables. The whole schema is Python dataclasses in the repo; the only state the engine itself creates at runtime is the Redis idempotency claim and the GCS run blob. Everything else is written by destination endpoints that already existed.

The declaration chain: a template owns columns; a ref column names an option source; validation materializes the source into a ResolvedOptions (values, spelling index, labels, dependents) once per validate call. value_space exists because the same entity is addressed differently per column: a location is a name in teammates.location but an id in digital_stores.bname_id (schema.py:16-20).

Division of labor

  • import_engine/schema.py — the dataclasses and their self-checks. ImportColumn.__post_init__ rejects a ref without an option source, an enum without enum_values, and multi on a non-multi-capable type.
  • import_engine/templates.py — the 15 declarations. Registry, validator, and wire format import without the web stack; heavy modules load lazily inside resolvers and appliers.
  • import_engine/option_sources.py — the 9 resolvers, reusing the /csv/dropdown/* functions verbatim so there is exactly one copy of the SQL.
  • import_engine/validator.py — the three tiers, uniqueness, existence, the wand.
  • import_engine/serialize.py — the wire format (validated_by per column) and the sample-CSV generator (formula-injection escaped, CWE-1236).
  • import_engine/appliers.py + run_log.py — the 5 write adapters, the run blob, the structured logs.
  • api_routers/import_router.py — the 5 endpoints, tenant resolution, the idempotency claim, the partial-import gate. Mounted via data_proxy_router into every service that includes it — six today: admin, balance, data_proxy, frontend_data, internal and store_uptime.

The system

Why not CSVBox

CSVBox is the hosted CSV widget Loop used for every bulk upload. Five classes of shipped failure forced the replacement; each one maps to a specific engine mechanism.

#the CSVBox failure (the scar)the engine mechanism
1No entity tier. CSVBox could not check a value against a live, chain-scoped set, so "Kanpur Central is not one of your locations" arrived only after the destination rejected the payload — or never, when the destination silently accepted it.ENTITY-tier validation runs before apply: the error lands on the cell while the customer is still looking at the grid (validator.py:15-21).
2Tenant in the querystring. Every /csv/dropdown/* route took csvbox_chain from the URL because the widget could not send a bearer token — any caller could enumerate another chain's locations, franchisees and users by editing a parameter. The v1 access-level dropdown also read a global Firestore collection, leaking custom roles across tenants.Tenant from the bearer token, always; ?chain= honoured for internal users only (403 otherwise). Only the v2, chain-scoped option sources are registered; v1 is deliberately absent (option_sources.py:189-192).
3Insert-only sheets. Every sheet except Locations was insert-only, so re-uploading a corrected file duplicated rows.upsert_key is a required field of every template; it also powers in-file duplicate detection, so a file that contradicts itself fails the second row instead of last-write-wins (schema.py:211-223, validator.py:276-302).
4Brittle matching. Comparison was case-sensitive: Downtown against a stored downtown failed with "value not in list". A non-ASCII display_label (an em-dash) made the widget silently fall back to the raw value.All matching is case-insensitive with canonical casing handed back; labels are built with plain ASCII hyphens (option_sources.py:15-17, csvbox_router.py:20-30).
5Schema in a vendor dashboard. The sheet definitions drifted from the frontends reading them: sheet 21651 had no id column even though the frontend read row.id and row.owner_id, so both were always null and onboarding uploads could never update. A broken dropdown made every ref cell fail "once per row, and customers could not tell a broken dropdown from bad data".Schema-as-code: the sample CSV, the grid, and the validator all read the same declaration. An empty option set becomes ONE import-level blocking error in its own words (validator.py:28-33).

Core lifecycle

Paste → check → fix → import

flowchart LR
  A["Open dialog"] --> B["Fetch template"]
  B --> C["Paste / drop CSV"]
  C --> D{"Headers map?"}
  D -->|"no"| C2["Refused at the door"]
  D -->|"yes"| E["Grid + browser cell tier"]
  E --> F["Check rows (server, 3 tiers)"]
  F --> G{"Report clean?"}
  G -->|"no"| H["Fix in grid / wand"] --> F
  G -->|"yes"| I["Import"]
  I --> J["Result + refetch"]

Any edit invalidates that row's server verdicts and the report's content key, so Import disables until a re-check. The report and the rows must match before apply is possible.

The happy path, numbered

  1. Open. The dialog fetches GET /imports/templates/{key} on every open and fully resets its state. The template is never cached: the browser always renders the schema the server will validate against.
  2. See the schema as the file. SchemaPanel shows a spreadsheet-style example with the real header row and up to two sample rows from the declaration. "Copy headers" and "Sample CSV" both come from the same declaration the validator reads.
  3. Paste or drop. parseDelimited (RFC 4180 — the official CSV spec — plus Excel's quirks: the invisible BOM marker at file start, Windows line endings, and cells that contain line breaks) auto-picks comma, tab or semicolon from the first line; mapHeaders maps case-insensitively by key then alias; toRecords trims and strips Excel's literal-text apostrophe armor. A window-level paste listener means Cmd+V works without clicking anything.
  4. Wrong file refused at the door. Zero matched headers, or any missing required column, rejects the file in the input phase with one message: "This doesn't look like a … file. Missing required column(s): …". One message here instead of seating it in the grid with two banners.
  5. Browser tier while you type. Required-blank for every column plus type checks for validated_by: "browser" columns, recomputed per keystroke. Messages match the server wording so a customer never sees two phrasings for one mistake.
  6. Check rows. POST /imports/templates/{key}/validate runs cell, row and entity tiers with the tenant's live option sets. Errors land per cell with tooltips and, when the server is confident, a one-click wand.
  7. Fix. Edits and wand clicks go through the same change path; each drops that row's stale server verdicts. Removing a row clears the whole report (row numbers shift).
  8. Import. POST .../apply with the rows, the content-hash idempotency key (a fingerprint computed from the file's contents), and allow_partial if the customer ticked the checkbox that only appears when the report has both valid and invalid rows.
  9. Result. Per-row outcomes (applied / updated / skipped / failed / invalid), a run id, a "Download the rows that did not import" CSV with an error column, and onApplied fires so the host screen refetches.

The guards protecting it

  • Partial-import refusal. By default one invalid row means nothing is written: apply 422s with the full report. Applying the valid subset requires an explicit allow_partial: true, and the skipped rows come back as explicit "invalid" outcomes. A partial landing must be an informed decision, never the CSVBox pattern of half-applied files nobody chose.
  • Backend re-validation. Apply re-runs all three tiers server-side no matter what the browser concluded. validated_by: "browser" is a latency optimization, never an authority: "we run it again because the browser is not trustworthy" (validator.py:10-11).
  • Idempotency. The dialog's key is an FNV-1a hash of the rows (a tiny, fast formula that crunches the rows into one short code: same rows, same code; change one cell and the code changes), so a double-click or network retry replays the same key and gets 409 "This file was already applied." within 15 minutes. Redis down means the guard degrades to unprotected rather than to an outage.

In-file uniqueness

In plain terms. Your file contradicting itself: two rows claim the same identity (the same upsert-key combo, e.g. the same platform + store_id). The second row goes red — "Row 1 already uses this key" — instead of the old behavior, where the last row silently won and you never learned the file disagreed with itself.

The tuple of upsert-key values per row is tracked; a repeat fails the second row with ENTITY-tier duplicate_in_file: "Row {first} already uses this {key list}." The scar: "Without this the last occurrence silently wins and the customer never learns the file contradicted itself." Rows where any key part is None are skipped, as are templates with an empty upsert key.

Existence rules

In plain terms. You upload a location row with no id (meaning "create new") but the name already exists on your chain. Nine times out of ten you meant to update that location and forgot the id — so instead of rejecting the row as a "duplicate", the error says "already exists (id 319909)" and offers a one-click fix that fills the id in, turning your create into an update.

Only user so far: locations.location_exists. A row with no id whose name already belongs to the chain gets already_exists — "{message} It is {label} (id {existing})." — with the machine fix "Use id {n}" targeting the id column. The scar: the old endpoint rejected that row as duplicate when it was really "an update the customer forgot to mark, not a new location". The rule's source is an option source whose index maps the other spelling back to the canonical value, which is exactly what makes the suggested fix exact. Skipped when unless_present (the id) has a value, when the cell is blank, or when the source resolved empty.

The wand contract

In plain terms. The wand is the one-click "fix it for me" button, and its rulebook is about never guessing: it appears only when there is exactly one obvious answer ("dave's dwntown" is clearly "Dave's Downtown"), never on ties ("loc 9" is equally close to loc 1 through 4), never for a well-formed value that simply belongs to someone else, and never when the "fix" would just trade one error for another. Clicking it replaces the whole cell, and it only ever turns the cell green.
  • RowError.fix = {column_key, value, label} where value is the full replacement cell content, applied verbatim by the client.
  • Single-value near-miss: offered only when exactly one legal value is a close match (difflib cutoff 0.78, ties suppressed). "loc 9" against loc 1..4 ties four ways and offers nothing; "dave's dwntown" resolves. A wrong-but-well-formed value (someone else's email) gets no button: "guessing a different human is not a fix."
  • REF_LIST whole-cell wand: all bad entries reported at once ("no whack-a-mole"); typos get replacements, unmatchable entries get removals, and the label names both halves ("Replace with 'X' and remove 'Y'") so the click is an informed choice. The wand appears only when clicking it turns the whole cell green — and is withheld entirely when the fix would empty a required cell: "a 'fix' that guarantees a required-blank error is no fix."

Message construction

In plain terms. The recipe for the red tooltip's sentence: quote exactly what you typed, get "is"/"are" right, pluralize the label, and show three real legal values plus a count ("...and 12 more") so you can orient without being buried. If the legal list itself failed to load, say that honestly ("We could not check...") instead of blaming your value. And one mistake gets one error: when the platform cell is wrong, the store-id cell that depends on it stays quiet — the parent owns the error.

_unknown_ref_message quotes every bad value, agrees the verb ("is"/"are"), pluralizes the column label, and samples three real legal values: "'Kanpur Central' is not among your locations. Yours include: A, B, C and 12 more." When the set could not be resolved at all: "We could not check {…} against your {labels}." Cascading courtesy: a child ref whose parent cell already failed carries its raw value through with no error — the parent owns the error, "so do not pile on".

How dual acceptance works

In plain terms. The engine builds a cheat sheet where every reasonable spelling points at the value that actually gets saved. For the location with id 319909 named Dave's Downtown, the sheet holds "319909" → 319909 and "dave's downtown" → 319909 — everything lowercased, so capitals never matter. Your cell is lowercased and looked up once; whichever spelling you typed, the right id lands in the database. "Alias failures are swallowed" means: if fetching the name spellings fails, the sheet simply has fewer rows — ids keep working, names temporarily do not, and nothing crashes.

_index maps both value.lower() and label.lower() of each canonical entry to the canonical value; then each alias entry — the same set resolved in the other value space — is joined on display label and its value indexed to the canonical. So "Dave's Downtown" and "319909" both resolve to whatever the column's canonical space is. NAME⇄ID uses the sibling bnames resolver; UID+EMAIL uses _users_by_email. Alias failures are swallowed (_safe) — dual acceptance degrades to single acceptance, never to an error. The users resolver is reimplemented in the module rather than calling get_user_options_v2 "because that endpoint returns a JSONResponse, not a list. Same query, same internal-user filter."

Cascading store_id: the dependents SQL

In plain terms. Think of a form with Country and City boxes: pick France, and the City box only accepts French cities — Tokyo is a real city, but it is not in France. Here platform is the Country and store_id is the City: your stores are sorted into per-platform buckets, and a row's store id is checked only against the bucket named by that row's platform cell, so a real DoorDash id on an ubereats row still fails. An empty bucket just means "no stores on that platform yet" — normal, not an error. CSVBox's one flat list could only ask "does this store exist anywhere?", so the wrong-platform row used to pass.

The platforms resolver's SQL (quoted from csvbox_router.py:33-66) is what powers store_id cascading:

select ds.* from digital_stores ds
join bnames b on b.id = ds.bname_id
join chains c on c.id = b.chain_id
where c.name = '<chain>'

Each platform entry carries "dependents": [{value: store_id}, …] filtered to that platform. A column with parent_column shares its parent's source and _narrow builds a fresh ResolvedOptions from dependents[str(parent_value)] — "so a DoorDash store id cannot be filed under Uber Eats", the dependency the flat CSVBox dropdown could not express. Cascading columns are exempt from empty-set blocking: an empty child set just means that platform has no stores. The platform list itself is the legacy PLATFORM enum plus every registered AI-SDK (Synapse) provider, ImportError-tolerant.

The validation-vs-apply scoping divergence (open scar). Validation's legal store ids come from the SQL above — chain membership via bnames.chain_id. But apply_digital_stores matches rows via DigitalStore → BName → ChainBNameMapping.chain_id. A bname whose chain_id is set but which has no chain_bname_mapping row — exactly what the old hasattr bug produced for bulk-inserted locations (rail 3) — yields a store that validates as legal but fails at apply with "Store ID not found". The converse (mapping row present, divergent chain_id) validates as unknown but would apply. Until the two reads are unified, treat "validated green, applied red" on digital stores as a mapping-row gap, not customer error.
In plain terms. Two clerks verify "is this store yours?" by different routes: the checker reads the chain id printed on the location itself; the saver looks the location up in a separate link table — the register. Usually they agree. But the old bulk-upload bug created locations with the printed field and no register entry, so a store there passes the check and then fails the save with "Store ID not found". Green checks, failed import. Until the two routes are unified: when digital stores go "validated green, applied red", look for the missing link-table row in our data — do not blame the customer's file.

The apply pipeline

In plain terms. The diagram is a sequence diagram: columns are participants, time flows down, each arrow is one message. The story of clicking Import: (1) the browser sends the rows plus the file's fingerprint; (2–3) the server re-checks everything, because browser green is not trusted; (4) if any row is bad and you did not tick "import the valid rows", it stops here with the full report — nothing written, and since the claim is only planted after this gate, a failed check never locks you out of retrying; (5–6) the double-click guard parks the fingerprint in Redis for 15 minutes — the identical submission gets "already in progress", while changing any cell makes a new fingerprint that goes straight through; (7) the rows go to the template's applier; (8–9) it saves one row at a time through the endpoint that already owned the table, each row reporting its own outcome; (10) a receipt of the run is written to cloud storage, and if that fails your import still succeeds; (11) the summary comes back and paints "Import complete".

  1. Template gate. 404 unknown key; 400 if the template has no applier ("'{label}' can be validated here but is still applied by its own screen.").
  2. Re-validate. The same validator.validate as the validate endpoint, server-side, regardless of what the browser said.
  3. Partial-import gate. 422 with the full report when there is any blocking error, zero valid rows, or invalid rows without allow_partial. The detail is report.as_dict() so the grid can re-seat every error.
  4. Idempotency claim. Key import_engine:idem:{tenant}:{template_key}:{idempotency_key}, Redis SET NX EX, TTL 15 minutes. No key supplied → always proceeds. Claim held → 409. Fail-open: any Redis exception logs "idempotency claim unavailable, applying anyway" and proceeds — "if Redis is unreachable we apply rather than block the customer". The claim precedes the applier, so a failed apply burns the key for 15 minutes too.
  5. Dispatch. ApplyContext(user, user_doc, tenant, db, request, demo). An applier's own HTTPException passes through; anything unexpected becomes 502 "The import could not be applied. Nothing further was written." carrying the run_id.
  6. Per-row, NOT transactional. The destinations commit row by row (per-row try/commit/rollback in repository/base.py, per-row independence in the teammates handler, per-row savepoints in the billing handler), so a file can still land half applied on write errors. That is what the run blob is for.
  7. Outcomes. With allow_partial, invalid rows are appended as explicit "invalid" outcomes carrying their first error; everything sorts by row_no.
  8. Run blob + logs. One JSON document to gs://{IMPORT_RUNS_BUCKET}/{chain}/{template}/{utcstamp}-{run_id}.json and structured import_engine.apply lines. Both fail-soft: "a logging or storage hiccup must never turn a successful import into a 500 after the rows are already written."

A store id validates only against the platform on the same row; a failed parent suppresses the child's error; cascading columns are exempt from empty-set blocking.A DoorDash store id filed under Uber Eats validating because it exists somewhere in the chain — the flat CSVBox dropdown could not express the dependency.
13Wand only when confident. One unambiguous close match (cutoff 0.78, ties suppressed); never for a well-formed wrong value; never when applying would blank a required cell; must turn the whole cell green.An auto-fix silently reassigning data to the wrong entity: "guessing a different human is not a fix"; "a 'fix' that guarantees a required-blank error is no fix".
14Existence rule with the exact fix. A no-id row whose name the chain already owns gets already_exists plus "Use id {n}".The old endpoint rejected it as duplicate when it was "an update the customer forgot to mark, not a new location" — the late error CSVBox pushed to the destination now lands on the cell, before apply, naming the id.
15Row cap. More than 5,000 rows → 413 "please split it into files of 5000 or fewer".A single validate/apply as a denial-of-service vector: every row fans out into option-set lookups and per-row destination writes; "a file this large is a sign the customer wants a different tool".

Runbooks & gotchas

Local stack

  • Postgres: dev loop_core is Homebrew PG on :5432 — note it sits on a divergent Alembic revision from prod; never assume schema parity.
  • Backend: any of the services that mount data_proxy_router serves /imports/*; frontend_data_service runs locally with uvicorn on PORT (default 5051). Backend tests need DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib on this Mac.
  • Frontend: Vite dev server (default :5173) from the app workspace. tsc carries ~1,460 pre-existing errors — always verify with a differential count, never an absolute one. eslint-plugin-react-hooks is installed but never registered, so rules-of-hooks never runs; run it manually before pushing hook changes. loop-admin's ESLint crashes on every file (ESLint 9 with only a legacy .eslintrc.json) — pre-existing.
  • Registry without the stack: import_engine imports without BigQuery/Firebase/Postgres — heavy modules load lazily inside resolvers and appliers — so validator.validate is runnable in a bare venv with option sources patched (that is exactly how the franchise dry run's verbatim JSON on these pages was produced; script: run_validate.py, patches option_sources.resolve with the chain's real values and calls the shipped code untouched).
